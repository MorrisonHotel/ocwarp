# AGENTS.md

Контекст для продолжения работы над репозиторием. Рассчитан на возврат через
полгода-год без внешних заметок. Язык общения и документации — русский.

## Что это

Portainer-стек из четырёх контейнеров в одном netns: ocserv (VPN) + 3proxy
(HTTP/SOCKS5), выход только через Cloudflare WARP (MicroWARP, ядерный WireGuard),
kill-switch в контейнере-владельце netns. Назначение: выход в интернет без утечки
реального IP сервера. Для пользователя — `README.md`.

Поставляется два файла: `README.md` и `docker-compose.yml`. Сборки образов нет,
все скрипты встроены в compose через `configs.content`. Их исходники — в `build/`.

## Чего в репозитории быть не должно

- Адресов, имён серверов, логинов и паролей. README и compose написаны обезличенно
  (`<сервер>`), так и оставлять.
- Файла `.pass` (пароль sudo для серверов, лежит в рабочем каталоге, не в индексе).
  `.gitignore` нет: перед `git add .` проверять `git status`. Содержимое `.pass`
  не печатать, передавать только через stdin (`sudo -S` из `read`).
- Описания промежуточных серверов, пробрасывающих трафик к этому стеку, и офисных
  клиентов. Это отдельные вещи, по решению владельца они здесь не упоминаются.

## Как устроен compose

- `docker-compose.yml` — сгенерированный файл, вручную не править. Источник:
  `build/compose.tmpl.yml` и `build/{killswitch.sh, wait-ready.sh, vpnuser.sh,
  proxy-start.sh, 3proxy.cfg, ocserv.conf}`. Сборка:
  `python3 build/gen.py build docker-compose.yml` — маркеры `__KILLSWITCH__` и т. п.
  в шаблоне заменяются телом файла с отступом 6 пробелов и `$`→`$$`
  (compose-интерполяция).
- Проверка после сборки: `docker compose config -q`; `git diff docker-compose.yml`
  должен показывать только ожидаемые изменения.
- Версии образов задаются тегом, не digest (решение владельца). Текущие:
  `ghcr.io/ccbkkb/microwarp:0.3.1`, `r4venme/ocserv:v1.6`, `3proxy/3proxy:1.0.2.busybox`.

## Инварианты kill-switch (не ломать)

Факты проверены на живом стеке и в netns-тестах. Любая правка `killswitch.sh`
должна их сохранять, после правки — прогон тестов из раздела «Проверка».

1. Через `eth0` наружу выходят только: пакеты с fwmark `0xca6c` (сокет WireGuard,
   метку ставит wg-quick) и пакеты направления `REPLY` по conntrack (ответы
   клиентам VPN и прокси). Всё остальное — DROP в `filter/OUTPUT` и повторно в
   `mangle/POSTROUTING` (цепочка `EGRESS`, видит фактический интерфейс выхода после
   перемаршрутизации по метке; `filter/OUTPUT -o` видит интерфейс до неё).
2. Ответы клиентам получают метку `0xca6c` в `mangle/OUTPUT` (`--ctdir REPLY`). Это
   единственный рабочий способ вывести их мимо `wg0`: wg-quick ставит своё правило
   `not fwmark 0xca6c → table wg0` всегда первым, любые ip-rule с собственным
   приоритетом проигрывают (правило без pref встаёт перед первым существующим).
3. В netns не использовать ip-rule с приоритетом 99 и 100: `firewall.sh` образа
   r4venme/ocserv удаляет их все при старте ocserv.
4. iptables в netns — legacy backend; ocserv держит свои правила в nftables
   (таблица `ip oc`), в `iptables -S` их не видно, смотреть `nft list ruleset` в
   контейнере ocserv. Таблицу `nat` kill-switch не сбрасывает: там правила Docker
   для резолвера `127.0.0.11`.
5. Встроенный DNS Docker (`127.0.0.11`) пересылает запросы наружу из этого же netns,
   то есть через `wg0` и под kill-switch. На время регистрации WARP (нет
   `warp/wg0.conf`) цепочка `BOOTSTRAP` открывает через `eth0` udp/tcp 53 и tcp 443
   только для uid 0. Без 53 регистрация падает с `SERVFAIL` (скачивание `wgcf`).
6. Старт при перезагрузке демона Docker не соблюдает `depends_on`: зависимые
   контейнеры ждут `state/ready` с идентификатором своего netns (`wait-ready.sh`).
   Если владелец netns пересоздан отдельно, остальные остаются в мёртвом netns без
   `eth0` — утечки нет, связи тоже; лечится пересозданием стека.
7. IPv6 в netns включён (ocserv выдаёт клиентам v6-маршрут в туннель, где v6
   отбрасывается), наружу закрыт `ip6tables` полностью.
8. MTU `wg0` = 1280, `OC_MTU` = 1280, MSS clamp в `mangle/FORWARD`.

## Поведение компонентов, на которое завязан стек

- MicroWARP 0.3.1: образ объявляет `VOLUME /etc/wireguard` (поэтому у netns там
  tmpfs); `wg-quick up` падает, если `wg0` уже есть — entrypoint warp сначала делает
  `down`; первая регистрация скачивает `wgcf` с GitHub.
- ocserv 1.6 (r4venme): шаблон `ocserv.conf` копируется в volume только при первом
  старте; ключи, задаваемые через `OC_*`, в шаблоне не нужны. Бан: неверный пароль
  10 очков, подключение 1, порог `max-ban-score = 80`, `ban-time = 300`,
  `ban-reset-time = 1200`. Все клиенты за одним NAT делят счёт. Бан включён по
  решению владельца (клиентов мало). `log-level = 1`: неудачные логины в журнал не
  попадают.
- 3proxy 1.0.2: без директивы `log` молчит; `include` пустого файла допустим,
  отсутствующего — фатален; `monitor` перечитывает файл раз в 60 с; `-a` убирает
  XFF/Via; UDP через SOCKS5 не работает за Docker NAT (порт UDP-ассоциации случайный).
- `vpnuser`: один логин/пароль в `ocpasswd` и `users.cfg` (`users логин:CL:пароль`);
  минимальная длина пароля 2 (решение владельца); пароль печатается только в
  терминал.

## Ловушки Docker/Compose/Portainer

- Изменение `configs.content` **не пересоздаёт контейнеры** ни в `docker compose up`,
  ни в Portainer «Update the stack». Способ из README: `docker rm -f` четырёх
  контейнеров, затем «Update the stack». Альтернатива — label с хешем конфигов на
  сервисах (предлагалась, владелец отклонил).
- Portainer при «Update the stack» с re-pull делает `compose pull`, который игнорирует
  `pull_policy: never`: сервис с локально собранным образом и `image:` без `build:`
  ломает деплой («pull access denied»). В этом стеке локальных сборок нет.
- Владелец деплоит через Portainer сам. По ssh на сервер — только читать и проверять,
  если прямо не попросили сделать иначе.

## Проверка после изменений

Тесты, которыми принят текущий стек (все пройдены). Повторять после любой правки
kill-switch, compose-сети или версий образов.

| # | Что | Ожидание |
|---|---|---|
| T1 | `curl` через прокси и из VPN на `cloudflare.com/cdn-cgi/trace` | `warp=on`, `ip` ≠ IP сервера |
| T2 | `tcpdump` на docker-bridge хоста под нагрузкой через прокси и VPN | 0 IP-пакетов (только ARP) |
| T3 | `docker exec ocwarp-warp wg-quick down wg0` | трафика нет, VPN-сессия жива, после `docker restart ocwarp-warp` работает |
| T4 | Заблокировать UDP до WARP-эндпоинта на хосте | трафика нет, на bridge пусто |
| T5 | Убрать `warp/wg0.conf`, перезапустить warp | клиентам VPN и прокси нет выхода; `curl` от root внутри netns через `eth0` проходит (по дизайну, только root) |
| T6 | Из VPN: шлюз Docker-сети, `10.10.10.1:3128`, ping `10.10.10.1` | первые два недоступны, ping работает |
| T7 | `nslookup` через `127.0.0.11` из контейнера + `tcpdump port 53` на bridge | имя разрешается, пакетов 0 |
| T8 | `reboot` сервера | все четыре в одном netns, `state/ready` совпадает, все `healthy` |
| T9 | `vpnuser del` | VPN рвётся сразу, прокси отвечает 407 не позже чем через 60 с |

Локально в WSL2 ядро без `xt_CONNMARK`; функциональные проверки правил делать в
`unshare -rnm` с veth и iptables-nft (legacy требует `touch /run/xtables.lock`
в tmpfs `/run`). Полные тесты — только на сервере.

Ловушки при тестировании: `curl --noproxy '*'` отключает и `-x`; в окружении WSL
могут стоять `HTTP(S)_PROXY` — запускать `env -i PATH=/usr/bin:/bin curl …`;
DROP/REJECT в OUTPUT возвращает ошибку сокету мгновенно, тесты на время нужно
делать с паузами; потери UDP по длинной цепочке ~5%, одиночные проверки флапают.

## Известные ограничения и неразобранное

- Пропускная способность выхода WARP измерялась ~16 МБ/с на одном потоке.
- Несколько клиентов за одним IP делят бан-счёт ocserv; автоматический клиент с
  неверным паролем (повтор каждые ~20 с) забанит общий IP за ~2 минуты. Возможная
  защита: `ban-points-connection = 0` (поддерживается в 1.6) и длинная пауза
  клиента после `Login failed`. Владелец решил пока не трогать.

## Стиль работы с владельцем

- Документация и комментарии: сухие факты о том, как работает, без истории решений.
  README — для пользователя стека, не для разработчика.
- Утверждения о работе сети подкреплять выводом команд (счётчики, tcpdump).
- Пошаговое руководство — по одному шагу на сообщение, с указанием места
  (**[сервер]** / **[клиент]**), командой и ожидаемым выводом.
- Ревью — в роли senior devops/network: сначала kill-switch, потом костыли и
  стандарты, потом производительность; после согласования — делать сразу.
